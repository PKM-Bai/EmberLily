# EmberLily 项目方案

确认日期：2026-11-01（Asia/Shanghai）。状态：**方案已确认，M0 阶段验收通过，M1 实施中**。依据包括工程与模拟器验证及用户 Thor 实机反馈；范围见 [M0 验证记录](M0_VALIDATION.md)，当前进展见 [M1 验证记录](M1_VALIDATION.md)。

本方案定义 EmberLily 的产品范围、工程边界和交付标准。用户已完成设计访谈并确认整体方案。实现任务见 [分阶段实施任务](IMPLEMENTATION_TASKS.md)，事实依据见 [技术依据与核验边界](TECHNICAL_EVIDENCE.md)。

## 1. 目标与使用场景

为 GBA《火焰纹章》官方作品和指定改版提供双屏增强体验：上屏运行原游戏，下屏持续显示信息、管理物品、制定培养方案、跟踪章节攻略，并研究和编辑游戏结构。

- 产品平台：Android；主要验收设备：用户的 AYN Thor 16GB＋1TB。
- 开发与数据验证在 Windows 上进行；桌面完整前端不属于首版交付。
- 实战、攻略与培养、研究与调试共同进入范围，按依赖顺序交付。
- 首版正常操作以背包／仓库为核心；移动、攻击等战场操作使用原生游戏流程。
- 开发阶段默认展示全部已解析数据，包括已验证的隐藏数据；后续增加独立开关与默认方案。
- 采用持续迭代，无硬性上线日期。用户负责目标样本和 Thor 实机体验，开发工作包含实现、适配及验证。
- 独立开源项目，采用 GPLv3 路线，选择性复用 pokedaisy 并保留要求的致谢。

“完整透视”意味着开放已经解析的数据。未识别的规则、技能或事件仍是未知，不应生成看似确定的结论。

## 2. 首版功能边界

| 功能 | 首版交付 | 后续增强 |
| --- | --- | --- |
| 战术分析 | 单位、阵营、装备、地形及已解析隐藏信息；光标详情；固定对比；移动与攻击覆盖；游戏当前战斗预测同步 | 任意位置、配装、技能组合的自由战斗模拟；下屏移动和攻击；自动行动编排 |
| 军团与背包 | 全军／仓库搜索筛选比较；准备画面整理与取放；战场合法交换、补给、装备和道具使用 | 批量配装方案、自动整理策略 |
| 培养规划 | 目标等级／职业、成长预期与概率范围、转职路线、属性上限和资源需求；多个方案保存、比较、跟踪 | 全队自动最优配队、全流程经验与资源优化 |
| 章节攻略 | 章节目标、外传条件、招募／对话、宝箱／村庄／商店、已解析增援和事件；完成状态与位置关联 | 剧情百科、逐回合最优通关路线 |
| 研究查看 | ROM／RAM 字段、人物／职业／物品／技能数据、事件标记和脚本、前后状态差异 | CPU 指令单步、汇编断点等底层调试器集成 |
| 研究编辑 | 单位属性／状态、物品／耐久、位置、行动状态及显式事件字段；修改前后值、恢复点与实验分支 | 完整强制招募、复活、跳章等剧情动作；永久 ROM 编辑与补丁导出 |

### 正常背包操作

正常操作遵循目标游戏的场景、距离、阵营、行动状态、物品可用性和容量限制。下屏缩短管理步骤，结果应与游戏内合法操作一致。

- 准备画面和战场使用不同的规则入口，分别验证。
- 装备、取放、交换和使用道具是不同命令；使用道具还要验证效果与行动状态。
- 跨距离转移、生成／复制物品、修复耐久属于研究编辑。
- 搜索、筛选和列表排序只影响显示。实际重排槽位或换装备必须由明确操作触发。
- 列表中的显示位置不能用作实际物品槽地址；执行时重新确认拥有者、原始槽位及内容。
- 一次交换或使用道具是最小一致性单元。多步队列逐项报告结果，不能暗示整队列天然具有全有或全无保证。

### 战术分析

攻击覆盖表示经过已验证规则计算的理论攻击范围，不代表敌方 AI 必然采取的行动。

当前战斗预测优先读取游戏在有效预测场景中已经计算的结果；不存在当前预测时明确显示暂无预测，不重复展示旧结果。自由模拟另设阶段，不能用原版公式代替尚未适配的改版规则。

### 研究编辑

首版编辑作用于运行状态，不修改原始 ROM 文件。部分运行状态修改会被游戏正常保存，所以实验分支必须拥有独立存档。

显式修改一个事件标记不等于执行完整事件。界面准确说明修改目标；一键复活并修复剧情、强制入队并补齐事件、跳章并完成前置流程等，作为后续专用命令适配。

## 3. 双屏与输入体验

上屏运行原游戏，下屏有战场、军团、培养、攻略、研究五个入口。默认战场视图显示光标对应的单位或地形，支持固定另一个单位对比；完整地图可切换查看。

- 手动固定内容或进入编辑时保持当前页面；回合变化只提示，不强制跳页。
- 攻略条目可以关联地图坐标、单位或研究数据，军团角色可以关联培养方案。
- 下屏触摸和手柄导航具有明确的控制归属；原游戏按键仍可使用。
- 切换输入目标时释放旧目标的按住状态，防止残留方向或抬键误落到游戏。
- 屏幕发现、显示器重绑、启动／退出、休眠恢复和帧缓冲释放统一由宿主管理。

## 4. 模块与数据边界

技术栈采用 Kotlin／Jetpack Compose、C/C++ JNI 和 mGBA。主界面、火纹模型与操作状态机新建；选择性复用 pokedaisy 的通用实现、测试模式及设备处理经验。

| 模块 | 责任 | 对外边界 |
| --- | --- | --- |
| GBA 运行核心 | mGBA 实例、模拟线程、帧推进、音视频、按键、内存捕获与帧间任务 | 普通 GBA 能力，不包含火纹人物、物品和事件定义 |
| Android 双屏宿主 | 屏幕、渲染、触摸／手柄、焦点和生命周期 | 提供输入意图与显示能力，不直接解析游戏数据 |
| 会话与存储 | ROM 身份、游戏存档、即时存档、恢复点、实验分支、操作记录 | 一致的会话恢复与分支切换 |
| 火纹适配与模型 | 身份识别、布局、文本／图像、单位／地图／物品／规则／事件 | 语义快照、数据来源、有效性和分能力支持声明 |
| 功能界面与命令服务 | 各工作区、分析、正常操作和研究编辑 | 接受语义命令，验证上下文并核对执行结果 |

数据链路为：ROM 静态资料与帧间 RAM 快照 → 构建适配器 → 共享火纹模型 → 各工作区。版本化攻略与规则资料包补充该模型；用户操作经命令服务返回对应适配器和运行核心。

### 适配器责任

地址、结构布局、文本解码、规则计算和可执行命令分别管理，避免将游戏差异散布到 UI。每个能力可以独立验证、启用或降级。

统一模型至少覆盖人物／职业定义、部署单位、物品与拥有者／槽位、章节、阵营阶段、光标、地图与地形、覆盖分析、当前战斗预测、事件条件及进度、玩家方案和自动事实。

原始字段、当前游戏有效值、推导结果和资料包说明保留各自来源。静态 ROM 数据与实时状态分别缓存；必要的指针和关联表跟随当前构建解析。

### 快照与对象身份

- 快照携带 ROM 身份、会话／分支、帧、状态版本、适配器版本和场景有效性。
- GBA RAM 在帧间捕获后异步解码；需要的其他内存区域明确加入采样范围。
- 光标、选中对象等快速状态与昂贵的全图分析分开更新；后台结果发布前核对状态版本。
- 读档、倒带、换 ROM、切章、研究恢复或分支切换后，失效的异步结果和排队命令不得重新写回。
- 单位身份不能只用角色 ID 或部署槽；需要考虑章节、实例生命周期及槽位复用。
- 物品操作确认拥有者、真实槽位、当前内容和状态版本，不假定同 ID 物品具有唯一实例编号。

### 命令执行

UI 提交语义意图；命令服务重新验证构建、场景、对象、库存和合法性，安排在合适的运行时机执行，重采样核验结果后再发布成功状态。

研究写入在稳定时机暂停执行，保留恢复点并记录前后值。需要跨帧完成的正常操作使用明确的进行中、取消、失败与恢复状态；重复提交不得重复执行。帧间可执行不代表任意 ROM 函数都能直接调用，具体入口须验证相关全局状态及副作用。

## 5. 存档与实验分支

只读研究不创建实验分支。进入可写研究模式时，从当前一致状态创建独立分支，隔离游戏状态、游戏存档及即时存档。

- 修改前保存恢复点，记录目标、前后值、对应构建与分支。
- 恢复时同步恢复游戏状态、相关存档与自动事实；不能只恢复 RAM。
- 游戏主动保存、重启实验及异常退出恢复均不得污染主游玩进度。
- 将实验结果设为主要进度时提升整个分支，旧主要进度保留为历史节点；首版不做状态字段的自动合并。
- 手写目标、培养方案与攻略笔记持续保留。自动成长、物品消耗及事件记录归属于对应时间线。
- 读回较早状态或倒带后，较晚事实留在原历史分支；当前状态重新采样和计算。
- 手写方案与恢复后的实际状态不一致时提示并重算，不删除用户意图。

自动事实只能根据已验证的事件或状态证据记录，不能把一次轮询差值包装成完整行动历史。

## 6. 培养与攻略数据

### 培养计算

从当前已实现的等级与属性出发，默认按正常推进计算，不假定反复读档刷成长。显示采用的成长、转职、上限、技能及资源规则；未知规则影响到结果时明确限制计算。

升级、转职、资源消耗、死亡或路线变化后重新计算预期、概率与需求。同一方案内有限资源不能重复分配，不同方案作为备选比较。

原始 RNG 状态可进入研究数据。首版不承诺所有未来随机结果预测或自动刷成长；通常成长概率与某次具体 RNG 结果分开表达。

### 章节资料

每条资料标记为游戏直接提取、版本资料包补充、规则推导或尚未解析，并记录适用版本。已完成状态来自经验证的游戏事实，资料说明本身不能被当作事件已经发生。

自动提取结合资料包逐步覆盖具体章节。含自定义代码或未解析分支的事件保留未知，提供研究入口，不补造确定攻略。资料覆盖情况和游戏功能兼容情况分别展示。

## 7. 作品覆盖与发布范围

固定适配顺序：

1. FE8 单一明确构建，建立最小双屏读写闭环。
2. FE7 基础适配；所需地区／布局结合目标文件核验。
3. 用户实际准备游玩的《天地之剑》指定中文构建。
4. 补齐 FE8、FE7 及该改版的首版功能矩阵。
5. FE6 独立适配，达到同一验收标准后加入。

每个支持项记录作品、地区／修订、改版／汉化构建、ROM 指纹、适配器版本、能力清单及验证证据。不能仅凭相同标题、game code、基础引擎或版本宣传名称认定布局一致。

未知构建保留模拟运行和原始研究入口；未经验证的语义分析与操作不能冒充完整支持。先能读取单位不意味着完整攻略、预测和操作已支持。

**v0.1 发布门槛为 M5：已锁定的 FE8、FE7 和《天地之剑》构建完成本方案首版功能及整体验收。FE6 在 M6 作为后续适配版本加入。** M1 与 M3 都是内部验证，不代表首版完成。

## 8. 里程碑

| 阶段 | 交付 | 验收门槛 |
| --- | --- | --- |
| M0 工程地基 | 精简 GBA 宿主、许可与复用清单、Thor 双屏、输入、基础保存、样本登记 | 启动／退出／保存／恢复稳定；输入归属正确；实验存储隔离 |
| M1 FE8 技术闭环 | 同帧读取、光标／单位／章节／物品、一次正常背包操作、一次研究编辑及恢复、回放样本 | 数据对照正确；操作和恢复结果正确；读档／切章后无旧状态回写 |
| M2 FE7 基础适配 | 第二套布局与规则，同一模型、UI 和命令接口 | 差异留在适配层；FE7 闭环与 FE8 回归通过 |
| M3 天地之剑接入 | 指定中文构建身份、文本、基础数据、必要操作及能力矩阵 | 使用改版本身的样本验证，列清功能缺口 |
| M4 功能补齐 | 战术、完整背包、培养、章节攻略、研究编辑及时间分支 | 三个目标构建逐项兑现首版功能，不以原版验证替代改版验证 |
| M5 Thor 整体验收 | 交互、性能、开关、兼容说明、文档和 APK | 三条功能主线可用，真实流程与状态转换通过，发布 v0.1 |
| M6 FE6 扩展 | 独立适配、文本／布局／规则差异及同等功能 | 通过相同验收标准后正式列入支持 |

M1—M3 先确定真实数据和命令边界。其后战术与军团 UI、培养计算、章节资料和研究工具可围绕稳定接口并行推进；共享核心修改与同一会话的写入验证按顺序执行。

M1 完成后依据实际宿主抽取与闭环投入估算后续工期；M3 完成后校准改版适配成本。当前不承诺日历日期。

## 9. 验收标准

以下编号用于任务和交付记录，适配新构建时复用同一标准并增加专有机制场景。

| 编号 | 必须验证的行为 |
| --- | --- |
| A01 支持身份 | 已支持构建有身份、能力及证据；未知构建不自动继承完整支持 |
| A02 实时对象 | 光标、选择／取消、回合切换后详情正确；固定对比稳定；死亡、离场、转职及槽位复用不串对象 |
| A03 战术分析 | 有效场景的原生预测逐项一致；覆盖分析只使用已验证规则；未知机制明确标记 |
| A04 数据隔离 | 切换作品或同作品不同构建后，不遗留名称、头像、规则、章节资料和缓存 |
| A05 背包完整性 | 搜索比较、准备整理、战场合法交换／补给／装备／使用均通过；归属、数量、耐久、效果和行动状态正确 |
| A06 操作一致性 | 执行前复核上下文；重复提交不重复生效；失效请求取消；失败无复制／丢失或虚假成功；多步操作逐项报告 |
| A07 纯显示排序 | 搜索筛选排序不改变实际槽位；显示条目始终映射正确操作对象 |
| A08 攻略状态 | 资料来源和覆盖明确；完成状态由游戏事实驱动；读档后自动进度回退，笔记保留 |
| A09 培养更新 | 升级、转职、资源变化和读档后重算；假设可解释；方案内资源不重复分配；手写目标保留 |
| A10 实验隔离 | 编辑、主动保存、重启和异常恢复只影响实验分支；原始 ROM 不变；修改目标和恢复点可核对 |
| A11 时间一致性 | 两个分支交替恢复时，游戏状态、存档、自动事实和分析一致；旧命令、引用及异步结果失效 |
| A12 Thor 连续流程 | 准备整理→地图查看／固定对比→合法交换／使用→原生预测→战斗／回合切换→保存读档→实验编辑→恢复，输入与显示行为正确 |

测试分为纯规则与解码测试、快照回放、模拟器集成验证、Thor 实机验证。代表状态包括标题／准备／地图／预测／动画／对话／转场，以及迷雾、救出、死亡、增援、转职和切章；按具体作品存在的机制增加样本。

每次交付列出实际通过、跳过和未覆盖的构建、能力与流程。不能用缺失样本而跳过的测试证明兼容。

性能目标为原速音视频稳定、下屏跟随及时、后台分析不阻塞模拟线程。用户已反馈 M0 在 Thor 持续运行时音视频无问题；本次未提供量化数据。M1 建立测量方法后锁定响应延迟与持续运行门槛。

## 10. 当前实施输入与风险处理

| 输入或风险 | 处理方式 |
| --- | --- |
